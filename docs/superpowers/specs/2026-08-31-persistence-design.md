# Persistence Tasarımı — Domain Entity'leri, DbContext, İlk Migration

**Tarih:** 2026-08-31
**Kapsam:** PLAN.md Faz 1
**Durum:** Onaylandı

## Bu Doküman Ne Değildir

Domain modelinin *ne* olduğu ve *neden* öyle olduğu `CLAUDE.md`'de yazıyor — entity listesi,
sahiplik/yetkilendirme kuralı, silme davranışı kararları, 3NF kuralları ve gelecek fikirler
oradadır ve tek doğruluk kaynağı orasıdır. Bu doküman onu **kopyalamaz**; yalnızca CLAUDE.md'nin
açık bıraktığı **persistence seviyesi kararları** kayda geçirir. Çelişki olursa CLAUDE.md kazanır.

## 1. Yerleşim ve Temel Tipler

### Klasör düzeni

```
src/Grind.Api/
├─ Models/
│  ├─ Entities/       User, Exercise, WorkoutTemplate, TemplateExercise, WorkoutSession,
│  │                  SetEntry, BodyWeightLog, ExerciseMedia, AiInsight  (9 dosya)
│  └─ Enums/          ExerciseCategory, RecordType, MediaType, AiInsightKind
└─ Data/
   ├─ AppDbContext.cs
   ├─ Configurations/ Her entity için bir IEntityTypeConfiguration<T>  (9 dosya)
   └─ Migrations/     dotnet ef tarafından üretilir
```

`OnModelCreating` tek satırdır: `ApplyConfigurationsFromAssembly(...)`. Gerekçe: tüm
yapılandırma tek metotta toplanırsa o dosya dokuz farklı sebeple değişir — SRP ihlali.

### Ortak taban sınıf yok

`BaseEntity` yazılmıyor. Dokuz entity'de `long Id` tekrarı **yapısal** bir tekrardır, bilgi
tekrarı değil — DRY bunu hedeflemez. Taban sınıf hiçbir davranış kazandırmadan tüm entity'leri
birbirine bağlar ve zamanla "audit alanları da buraya" baskısı yaratır. `CreatedAt` de ortak
değildir: bazı entity'lerde vardır, `WorkoutSession`'da karşılığı `StartedAt`'tir.

### Tip kararları

| Konu | Karar | Gerekçe |
|---|---|---|
| `Id` | `long`, `GENERATED BY DEFAULT AS IDENTITY` | Kullanıcı kararı |
| Enum'lar | `HasConversion<string>()` → `text` | Enum üyelerinin sırası değişse veya araya yeni üye girse de mevcut satırların anlamı kaymaz |
| Zaman damgaları | `DateTime` (Kind=Utc) → `timestamp with time zone` | `DateTimeOffset` gereksiz: her zaman UTC saklanır, TR yerel saatine çevirme yalnızca sorgu katmanında yapılır. Npgsql'in `timestamptz` yazarken Kind=Utc dışındaki değerlerde hata verdiği biliniyor; bu davranışa güvenmeden önce Faz 1 testinde doğrulanacak (§5, madde 11) — doğrulanırsa UTC kuralı çalışma zamanında kendiliğinden zorlanmış olur |
| `Weight` | `decimal(6,2)` | `double` kayan nokta hatası taşır; ağırlıkta kabul edilemez. Maks. 9999.99 |
| `Reps`, `PlannedSets`, `OrderIndex` | `int` | — |
| `Rir` | `int?` | CLAUDE.md: nullable |
| `EstimatedCostUsd` | `decimal(10,6)?` | LLM maliyetleri 0.000042 USD mertebesinde; `(10,2)` her şeyi sıfıra yuvarlardı |
| Navigation | Zorunlu olanlar `= null!;`, koleksiyonlar `= [];` | Nullable reference types açık |

### Entity stili: anemik POCO

Entity'ler public get/set taşıyan düz veri sınıflarıdır. Tüm iş kuralı (pozitif tekrar, sahiplik
kontrolü, PR tespiti) Service katmanında yaşar — CLAUDE.md'nin katman tanımı ve `solid-dry-kiss`
skill'i bunu söylüyor. Kapsüllenmiş domain modeli (private setter + invariant zorlayan
constructor) bu ölçekte EF materialization'ı, `HasData` seed'i ve migration'lar için gereksiz
tören getirirdi. İleride birkaç alanı `required`/`init` yapmak maliyetsizdir.

## 2. Alan Detayları

CLAUDE.md'deki domain modeline ek olarak yalnızca uzunluk/precision kararları:

| Entity | Ek karar |
|---|---|
| User | `Username` string(50), **lowercase saklanır** · `PasswordHash` string(100) |
| Exercise | `Name` string(100) |
| WorkoutTemplate | `Name` string(100) |
| WorkoutSession | `Notes` sınırsız `text` |
| ExerciseMedia | `Url` string(500) |
| AiInsight | `Content` sınırsız `text` · `Model` string(100) |

### Username case-insensitivity

Kayıt sırasında `ToLowerInvariant()` uygulanır; veritabanında her zaman küçük harf durur ve tek
bir unique index yeterlidir. `citext` eklentisi kullanılmadı (migration'a `CREATE EXTENSION`
girerdi ve test altyapısını gerçek Postgres'e bağımlı kılardı); ayrı bir `NormalizedUsername`
sütunu da kullanılmadı (başka bir non-key alandan türetilirdi — 3NF ihlali). Bedeli: kullanıcının
yazdığı büyük/küçük harf düzeni korunmaz. Kişisel bir antrenman uygulamasında kabul edilebilir.

### SetEntry'de UserId yok

Sahiplik `WorkoutSession.UserId` üzerinden türetilir. `SetEntry`'ye `UserId` eklemek o alanı
`WorkoutSessionId` üzerinden transitive bağımlı hale getirirdi (3NF ihlali) ve senkron kalması
gereken ikinci bir doğruluk kaynağı yaratırdı. Bedeli: PR motorunun temel sorgusu ("bu
kullanıcının bu egzersizdeki tüm setleri") bir join gerektirir; bu, aşağıdaki index'lerle
karşılanır. Faz 8'de ölçülebilir bir performans sorunu çıkarsa o zaman somut veriyle yeniden
değerlendirilir — şimdiden denormalize etmek YAGNI.

## 3. İlişkiler, Silme Davranışları, Kısıtlar

### Silme davranışları

| İlişki | Davranış | Kaynak / gerekçe |
|---|---|---|
| WorkoutTemplate → TemplateExercise | CASCADE | CLAUDE.md (composition) |
| WorkoutTemplate → WorkoutSession.TemplateId | SET NULL | CLAUDE.md |
| WorkoutSession → SetEntry | CASCADE | CLAUDE.md |
| Exercise → SetEntry | RESTRICT | Exercise hard-delete edilmiyor; kazara silme sessizce geçmişi uçurmak yerine gürültüyle patlamalı |
| Exercise → TemplateExercise | RESTRICT | aynı |
| Exercise → ExerciseMedia | CASCADE | Egzersizsiz medya anlamsız |
| User → tüm sahip olduğu kayıtlar | **RESTRICT** | aşağıya bakınız |
| AiInsight → WorkoutSession / SetEntry | SET NULL | aşağıya bakınız |

**User → RESTRICT (açıkça yapılandırılır, EF varsayılanı DEĞİLDİR).** İki tuzak vardır:
zorunlu FK'lerde EF varsayılanı CASCADE'dir — bir kullanıcıyı silmek sessizce tüm antrenman
geçmişini uçururdu. Daha kötüsü, `Exercise.UserId` nullable olduğu için EF varsayılanı SET
NULL'dır: kullanıcı silinince onun özel egzersizleri `UserId = null` olur, yani **global
egzersize dönüşüp herkeste görünür**. Her iki yol da kapatılır.

Hesap silme bir özellik olarak planlanmıştır (PLAN.md Faz 13) ve bu karar onunla çelişmez, onu
destekler: CASCADE'e geçilseydi `User → Exercise` ile `Exercise → SetEntry (RESTRICT)` çakışan
iki silme yolu oluşur ve silme çalışma anında hata verirdi. RESTRICT ile hesap silme, Service
katmanında tek transaction içinde sıralı ve bilinçli bir işlem olur; neyin silindiği okunur ve
test edilebilir.

**AiInsight → SET NULL.** Bir session silindiğinde ona ait AI yorumu silinmez, yalnızca
bağlantısını kaybeder. Gerekçe: `AiInsight` aynı zamanda bir maliyet kaydıdır (`TokensUsed`,
`EstimatedCostUsd`); "bugüne kadar AI'ya ne harcadım" sorusu, bir session silindi diye yanlış
cevap vermemelidir.

### Index'ler

| Index | Amaç |
|---|---|
| `User(Username)` UNIQUE | Kimlik |
| `Exercise(UserId, Name)` UNIQUE, NULLS NOT DISTINCT | aşağıya bakınız |
| `WorkoutSession(UserId, StartedAt)` | Geçmiş sorgusu, takvim/streak, "bugünkü açık session" |
| `SetEntry(ExerciseId, WorkoutSessionId)` | PR motorunun ana sorgusu |
| `BodyWeightLog(UserId, RecordedAt)` | Zaman ekseninde karşılaştırma |
| `AiInsight(UserId, CreatedAt)` | Geçmiş yorumların listelenmesi |
| `TemplateExercise(WorkoutTemplateId, OrderIndex)` | Sıralama. **Unique değil** — gerçek programlarda aynı hareket bir günde iki kez geçebilir |

**`Exercise(UserId, Name)` ve NULL tuzağı.** PostgreSQL'de NULL'lar birbirinden farklı sayılır,
bu yüzden düz bir unique index `(null, 'Bench Press')` satırının iki kez eklenmesini engellemez —
yani global egzersizlerde hiçbir şey korumaz. PostgreSQL 15+ `NULLS NOT DISTINCT` kullanılır
(Npgsql: `.AreNullsDistinct(false)`). Sağlayıcı bunu desteklemiyorsa iki kısmi index'e düşülür:
`WHERE UserId IS NOT NULL` ve `WHERE UserId IS NULL`. Sonuç aynıdır.

**Bu index'in ifade EDEMEDİĞİ kural:** "kullanıcı, var olan bir global egzersizin adını kendi
özel egzersizi olarak ekleyemesin" — farklı `UserId` değerleri olduğu için bir DB kısıtıyla
yazılamaz. Bu kontrol ve isimlerin büyük/küçük harf normalizasyonu Faz 5'te Service katmanında
yapılır (CLAUDE.md: "en azından uygulama katmanında kontrol edilmeli").

**Arşivleme ve isim çakışması.** `IX_Exercises_UserId_Name` benzersiz kalır ve bir egzersiz
arşivlenince (`IsArchived = true`) adı serbest bırakılmaz — bu bilinçlidir: `WHERE NOT
"IsArchived"` gibi kısmi bir index kullanılsaydı, aynı isim bir satır arşivliyken ikinci bir
satıya (aynı `UserId` altında) geçebilirdi, ki bu iki farklı "Cable Crossover" kaydının aynı
anda var olması demektir — istenen bu değil. Bedeli: kullanıcı kendi "Cable Crossover"ını
arşivleyip sonra aynı isimle yeniden eklemeye çalışırsa ham PostgreSQL `23505` (unique
violation) hatası alır, yani işlenmemiş bir 500. Index doğru olduğu için düzeltme burada değil,
Faz 5'te: Service katmanı yeni egzersiz eklerken "bu isim zaten var ve satır arşivli" durumunu
bir çakışma (409) olarak değil, bir **arşivden çıkarma** (unarchive: `IsArchived = false`)
işlemi olarak ele almalı.

**Kısıtlanamayan çapraz kullanıcı referansları.** Yukarıdaki gibi bir ilişkisel şema, "bu FK
başka bir kullanıcıya ait bir satırı işaret etmesin" kuralını kendi başına ifade edemez — bunun
için her tabloda composite `(Id, UserId)` anahtar ve composite foreign key gerekirdi; bu, bu
ölçekteki bir kişisel uygulama için haklı çıkarılamayacak gerçek bir karmaşıklık artışıdır
(bkz. `solid-dry-kiss`, YAGNI). Bu yüzden aşağıdaki dört durumun her biri, CLAUDE.md'nin zaten
belirttiği genel sahiplik/yetkilendirme kuralının (bkz. CLAUDE.md "Yetkilendirme Kuralı") somut
bir örneğidir ve ilgili fazda açık bir Service-katmanı sahiplik kontrolüne dönüşür — hiçbiri DB
seviyesinde yakalanmaz:

- `TemplateExercise.ExerciseId`, başka bir kullanıcının özel egzersizini işaret edebilir →
  Faz 6 (WorkoutTemplate) bunu doğrulamalı.
- `WorkoutSession.TemplateId`, başka bir kullanıcının şablonunu işaret edebilir → Faz 7
  (WorkoutSession) bunu doğrulamalı.
- `SetEntry.ExerciseId`, başka bir kullanıcının özel egzersizini işaret edebilir → Faz 8
  (SetEntry + PR motoru) bunu doğrulamalı.
- `AiInsight.WorkoutSessionId` / `AiInsight.SetEntryId`, başka bir kullanıcının session'ını
  veya setini işaret edebilir → Faz 12 (AiInsight altyapısı) bunu doğrulamalı.

Bu liste, ilgili fazlar CLAUDE.md'yi yeniden okumadan bu yükümlülüğü unutmasın diye buradadır —
kural yeni değildir, sadece burada somutlaştırılmıştır.

### CHECK kısıtları

Uygulama doğrulamasının yerine değil, son savunma hattı olarak:

- `Reps > 0`
- `PlannedSets > 0`
- `Rir IS NULL OR Rir >= 0`
- `EndedAt IS NULL OR EndedAt > StartedAt`
- `SetEntry.Weight >= 0` — **sıfır dahil**: barfiks, dips gibi vücut ağırlığı hareketleri
  0 kg'dır. Faz 8'i de ilgilendirir: 0 kg'lık bir harekette ağırlık rekoru hiç kırılmaz, yalnızca
  tekrar rekoru işler; PR motoru bunu ek bir özel duruma gerek kalmadan doğal olarak ele alır.
- `BodyWeightLog.Weight > 0` — burada sıfır dahil değildir: `SetEntry.Weight` bir harekette
  kaldırılan ek ağırlığı temsil eder (0 = sadece vücut ağırlığı, geçerli bir değer), ama
  `BodyWeightLog.Weight` kullanıcının kendi vücut ağırlığının doğrudan ölçümüdür — hiçbir insan
  0 kg değildir, bu yüzden burada kısıt `>= 0` değil `> 0`'dır.

## 4. Seed ve Migration

### Global egzersizler (15 satır, `UserId = null`)

| Kategori | Egzersizler |
|---|---|
| Push | Bench Press, Incline Dumbbell Press, Overhead Press, Dips, Triceps Pushdown |
| Pull | Pull-up, Barbell Row, Lat Pulldown, Barbell Curl, Face Pull |
| Legs | Squat, Deadlift, Romanian Deadlift, Leg Press, Leg Curl |

Deadlift Legs kategorisindedir. Bu bir tercih meselesidir (birçok program onu Pull gününde
yapar) ve kullanıcı isterse tek satırlık bir seed değişikliğiyle taşınır.

### Identity sequence çakışması ve çözümü

`HasData` ile `Id = 1..15` sabit değerleri identity sütununa yazıldığında PostgreSQL'in identity
**sequence'i ilerlemez**; hâlâ 1'den başlamaya hazır bekler. Kullanıcı ilk özel egzersizini
eklediğinde veritabanı `Id = 1` üretmeye çalışır ve seed satırıyla çakışır.

Çözüm, migration'ı elle düzenlemek değil (CLAUDE.md yasaklıyor), yapılandırmadır:

```csharp
builder.Property(e => e.Id)
       .UseIdentityByDefaultColumn()
       .HasIdentityOptions(startValue: 1000);
```

Seed 1–15 aralığını tutar, kullanıcı kayıtları 1000'den başlar. Migration yine
`dotnet ef migrations add` ile üretilir.

## 5. Doğrulama Stratejisi

Testler implementasyondan **önce** yazılır. EF Core'un `AppDbContext.Model` nesnesi veritabanına
hiç bağlanmadan okunabilir; bu sayede aşağıdaki iddialar gerçek Npgsql sağlayıcısıyla, Docker
gerekmeden doğrulanır — yani üretimde kullanılacak modelin ta kendisi test edilir:

1. `WorkoutSession → SetEntry` CASCADE
2. `Exercise → SetEntry` ve `Exercise → TemplateExercise` RESTRICT
3. `User → Exercise` RESTRICT (SET NULL **değil**)
4. `WorkoutTemplate → WorkoutSession.TemplateId` SET NULL
5. Tüm enum property'leri `string`'e dönüşüyor
6. Tüm `DateTime` property'leri `timestamp with time zone`
7. `Weight` sütunları `numeric(6,2)`
8. `User(Username)` ve `Exercise(UserId, Name)` unique index'leri mevcut
9. 15 seed satırı modelde tanımlı ve hepsinin `UserId`'si null
10. `Exercise.Id` identity başlangıç değeri 1000
11. `Kind` değeri `Utc` olmayan bir `DateTime` yazmaya çalışmak hata veriyor (yukarıdaki tip
    kararının dayandığı varsayımın doğrulanması) — bu tek madde bağlantı gerektirdiği için
    Docker ayağa kalktıktan sonra çalıştırılır

Docker yalnızca son adımda gerekir: `dotnet ef database update`, 11. maddenin testi ve psql ile
tabloların, seed satırlarının, CHECK kısıtlarının gözle doğrulanması.

Not: Faz 0'da test projesine eklenen `Microsoft.EntityFrameworkCore.Sqlite` paketi Faz 1'de
kullanılmıyor (model testleri gerçek Npgsql sağlayıcısıyla çalışıyor). Servis katmanı testlerinde
de gerekmediği ortaya çıkarsa paket kaldırılacak — kullanılmayan bağımlılık bırakılmaz.
